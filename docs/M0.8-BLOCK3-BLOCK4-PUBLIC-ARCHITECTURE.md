# M0.8 Block 3 and Block 4 — Public Architecture and Delivery Model

Status: Public explanatory documentation  
Scope: M0.8 Block 3 (GitHub Action) and M0.8 Block 4 (Distribution and Release)  
Implementation source of truth: the workflow and Action files referenced below

## Purpose

M0.8 introduced two distinct ways to consume Android Release Doctor:

1. GitHub Action — use Android Release Doctor inside a GitHub Actions CI pipeline.
2. Distributed CLI — download a versioned executable package and run Android Release Doctor locally or from another automation environment.

These are complementary delivery surfaces. They are not duplicate workflows and they do not have the same responsibility.

This document explains the public architecture of both surfaces and how they fit together.

---

## 1. M0.8 Block 3 — GitHub Action

Workflow:

- .github/workflows/m08-block3-action.yml

Composite Action:

- .github/actions/android-release-doctor/action.yml

### What Block 3 provides

Block 3 validates Android Release Doctor as a reusable GitHub Actions component.

Conceptually:

GitHub CI pipeline
    |
    v
Android Release Doctor Action
    |
    v
validated Android Release Doctor CLI
    |
    +--> report
    +--> exit code

A consuming workflow can provide an APK or AAB and receive a report plus a machine-readable process result.

### How the self-test is triggered

The Block 3 workflow currently validates:

- pushes to the m08-block3-github-action branch;
- pull requests targeting m08-block2-cli-output-contract.

The branch filters are part of the historical stacked-development validation model used by this repository. They are validation infrastructure, not part of the Action's user-facing input contract.

### The Action input contract

The current composite Action accepts:

- artifact — required APK/AAB path;
- project — optional Android application module path;
- play — optional Google Play readiness profile switch;
- play-platform — platform passed to the Play profile;
- format — text or json;
- output — optional report output path.

The Action internally invokes the repository's validated doctor-cli through Cargo and maps the supplied inputs to the corresponding CLI arguments.

### The Action output contract

The Action exposes:

- exit-code — the exact Android Release Doctor process exit code;
- report-path — the report output path when one was supplied.

This makes the Action usable by later CI steps without requiring them to interpret human-readable console output.

### Block 3's three validation paths

The public self-test intentionally exercises three distinct outcomes.

#### A. Successful audit

A valid fixture is audited with JSON output.

The workflow verifies:

- the Action returns a report path;
- the report exists and is non-empty;
- the Report v1 schema version is 1.0;
- the report contains findings;
- the report contains summary.

This proves that the Action does more than start successfully: it produces the expected machine-readable result.

#### B. Blocker detected

The workflow enables the Play readiness profile against the fixture and expects:

    exit code = 1

It also verifies that the resulting report contains one or more blockers.

Exit code 1 is therefore treated as an expected audit result, not as an Action implementation failure.

#### C. Operational error

The workflow intentionally supplies a non-existent artifact and expects:

    exit code = 2

This distinguishes an operational/usage failure from an audit that completed and found blockers.

### Exit-code model

The current CLI/Action contract is:

| Exit code | Meaning |
|---|---|
| 0 | Audit completed with no blockers |
| 1 | Audit completed and one or more blockers were found |
| 2 | Usage, input/audit, output, or internal serialization/operational error |

This distinction is important for CI automation because a pipeline can react differently to a product-release blocker and to a broken invocation.

## 2. M0.8 Block 4 — Distribution and Release

Workflow:

- .github/workflows/m08-block4-distribution.yml

### What Block 4 provides

Block 4 turns the validated CLI into versioned, platform-specific distribution packages.

Conceptually:

source
  |
  v
validate
  |
  v
release binary
  |
  +--> Linux package
  +--> Windows package
  +--> macOS package
  |
  v
SHA256SUMS
  |
  v
GitHub Release

This is the downloadable product surface rather than the reusable CI Action surface.

### How Block 4 is triggered

The current workflow validates:

- pushes to the m08-block4-distribution-release branch;
- pull requests targeting m08-block3-github-action.

A tag matching v* additionally enables the publication path.

For example:

- v0.1.0
- v0.2.0
- v1.0.0

can enter the release-publication path when the corresponding repository state passes validation.

### Step 1 — Validate

The validate job:

1. checks out the repository;
2. reads the workspace version from Cargo.toml;
3. when running from a version tag, verifies that the tag version matches the workspace version;
4. runs:
   - cargo test --workspace --locked;
   - cargo fmt --all -- --check;
   - cargo clippy --workspace --all-targets --locked -- -D warnings.

This means packaging is downstream of code validation.

A package is not considered ready merely because compilation succeeded.

### Step 2 — Package

The package job builds a release binary and uses a platform matrix for:

| Platform | Runner | Package |
|---|---|---|
| Linux x86_64 | ubuntu-24.04 | tar.gz |
| Windows x86_64 | windows-2025 | zip |
| macOS x86_64 | macos-15-intel | tar.gz |

Each package currently contains exactly the executable plus:

- LICENSE;
- README.md.

The executable is checked with --version and --help before the package is accepted.

The archive itself is then inspected to verify its expected contents.

### Step 3 — Upload validated package artifacts

Each platform package is uploaded as a GitHub Actions artifact.

The workflow keeps these temporary CI artifacts for a limited retention period and uses them as inputs to the publication job.

### Step 4 — Publish only from a version tag

The publish job runs only when:

- the event is a push;
- the pushed ref is a version tag beginning with v;
- validation passed;
- all platform package jobs passed.

This creates a deliberate boundary:

    branch push      -> validate/package only
    pull request     -> validate/package only
    version tag      -> validate/package/publish

### Step 5 — Checksums

Before publication, the workflow collects the three packages and generates:

    SHA256SUMS

It then verifies the generated checksum file against the package files.

This gives users an integrity check independent of the GitHub Release UI.

### Step 6 — GitHub Release

The workflow publishes the three platform packages plus SHA256SUMS as a GitHub Release and uses the tag as the release identity.

The publication step also uses tag verification and generated release notes.

---

## 3. Permission boundary

The distribution workflow deliberately separates read-only validation from publication.

The validate and package jobs use:

    permissions:
      contents: read

The publish job is the only part that requires:

    permissions:
      contents: write

This limits write access to the smallest part of the release process that needs it.

---

## 4. Why Block 3 and Block 4 are separate

The two blocks solve different user problems.

### Block 3 — CI integration

The question is:

> How do I make Android Release Doctor part of my GitHub build/release pipeline?

The answer is the reusable Action.

    APK/AAB -> Action -> report + exit code

### Block 4 — product distribution

The question is:

> How do I obtain Android Release Doctor as a program I can run?

The answer is the platform-specific release package.

    source -> release binary -> package -> GitHub Release

They can therefore evolve independently while remaining complementary.

---

## 5. Evidence-first package philosophy

Block 4 intentionally performs more than a compilation step.

The release path validates:

- source/test state;
- formatting;
- linting;
- release binary creation;
- executable --version;
- executable --help;
- required package files;
- archive contents;
- package checksums;
- tag/version consistency.

The objective is to make a published package a validated release artifact, not merely an archive produced by CI.

The repository's error ledger records packaging and cross-platform corrections made during M0.8, including lockfile reproducibility and platform-dependent archive verification behavior. Those corrections are part of the engineering history that shaped the current validation path.

## 6. Evolution and incremental improvement

Neither Block 3 nor Block 4 should be interpreted as permanently frozen.

Both are versioned, maintainable delivery surfaces and may receive future incremental improvements.

Possible future evolution includes, for example:

- additional Action inputs or outputs;
- improved input validation;
- additional report handling options;
- support for additional host platforms or CPU architectures;
- additional package formats;
- stronger package provenance or integrity metadata;
- release automation improvements;
- clearer onboarding and CI examples;
- compatibility improvements that preserve existing consumers.

Future changes should remain incremental and evidence-driven.

### Compatibility principle

When practical, improvements should preserve existing user contracts.

For the Action this includes particular care around:

- input names;
- input meanings;
- output names;
- exit-code semantics.

For distribution this includes particular care around:

- version/tag consistency;
- package naming;
- expected package contents;
- checksum verification;
- release publication semantics.

A breaking change may still be appropriate when necessary, but it should be explicit, documented, validated, and reflected in the corresponding release/onboarding material.

### Documentation maintenance rule

The actual workflow files and Action metadata remain the implementation source of truth.

This document is a public architectural explanation.

Therefore:

- implementation changes must not be considered complete merely because this document was edited;
- this document should be updated when the user-visible architecture or delivery contract changes materially;
- detailed implementation audits remain the authoritative historical validation records for their respective blocks.
