# M0.7 — Definition and Execution Plan

Date: 2026-09-30

## Status

**Etapa 3 — Definición de M0.7: EN CURSO**

This document defines the proposed M0.7 scope from the completed M0.6 transition audit. It does not implement production code and does not authorize implementation until this definition receives its own second audit, CI validation, and baseline checkpoint.

## 1. M0.7 objective

M0.7 will focus on one coherent axis:

**increase the completeness and precision of APK cryptographic verification without weakening the evidence-first model established in M0.6.**

The milestone will extend the verifier in controlled increments, preserving the existing distinction between:

- Verified;
- Invalid;
- Unsupported;
- ManualReview.

M0.7 will not attempt to solve every capability identified by the transition audit.

## 2. Included scope

### M0.7 Block 1 — Cryptographic coverage matrix

Establish an explicit Android v2/v3 verification coverage matrix covering:

- signature algorithm IDs;
- digest algorithms;
- key sizes/curves where applicable;
- currently supported combinations;
- deliberately unsupported combinations;
- exact evidence/result semantics for each boundary.

Work sequence:

1. audit current implementation against the applicable Android specification;
2. identify only the next bounded coverage increment;
3. add deterministic fixtures for supported, invalid, malformed, and unsupported cases;
4. implement the smallest scoped verifier change;
5. add focused regression tests;
6. run second audit and CI;
7. checkpoint before opening the next block.

No algorithm is considered supported merely because parsing succeeds. Cryptographic support requires real signature verification plus the relevant digest/key constraints.

### M0.7 Block 2 — Proof-of-rotation semantic evidence

Extend the existing M0.6 proof-of-rotation verification only where the Android specification gives a deterministic, locally verifiable semantic rule for lineage node flags.

Requirements:

- preserve all M0.6 lineage checks;
- model the relevant flags explicitly;
- distinguish malformed structure, known capability evidence, and unsupported/unknown flag bits;
- model the defined lineage capability bits explicitly rather than treating unusual bit combinations as inherently invalid;
- add fixtures covering representative capability states and unknown/reserved-bit handling where such bits can be encountered;
- validate semantic consequences only where Android defines a deterministic rule that can be checked from the artifact alone;
- preserve structured lineage evidence;
- do not infer broader Android runtime trust decisions that the artifact cannot prove.

If the specification or cryptographic backend leaves a semantic boundary uncertain, keep it as ManualReview/Unsupported rather than guessing.

### M0.7 Block 3 — v3.1 verification

Define and implement complete v3.1 verification for the supported algorithm subset only.

Requirements:

- detect and parse the v3.1 structure precisely;
- verify the v3.1 signature using the existing cryptographic verification path only for supported algorithms/key combinations;
- verify that a v3.1 block is paired with the required v3 base block;
- extract and verify the v3.1 rotation-min-SDK targeting semantics;
- verify the v3 stripping-protection attribute against the v3.1 rotation target;
- verify that the v3 and v3.1 signer/range sets are consistent for their targeted platform ranges, including required coverage and non-overlapping targeted ranges;
- verify signer/lineage consistency across platform-targeted v3/v3.1 signers;
- preserve multi-signer isolation;
- preserve SDK-range evidence;
- preserve proof-of-rotation evidence where applicable;
- distinguish unsupported cryptographic combinations from malformed or cryptographically invalid data;
- add deterministic v3.1 fixtures for valid, malformed, cross-block mismatch, missing-block, invalid-signature, and unsupported-algorithm cases.

The block must not silently treat v3.1 as ordinary v3 verification if the Android specification requires different cross-block or rotation-target semantics.

### M0.7 Block 4 — Integration and completeness checkpoint

After Blocks 1–3:

- perform a milestone-wide audit;
- compare implementation against the declared Android specification coverage;
- verify all supported/unsupported boundaries;
- review the complete incremental error ledger;
- validate all stacked CI paths;
- update README capability history;
- produce a final M0.7 audit and checkpoint.

## 3. Explicitly outside M0.7

The following remain outside this milestone unless a later transition audit formally changes the scope:

- full v3.2/PQC verification;
- full AAB signing/final-generated-APK verification workflow;
- Gradle execution or complete variant resolution;
- complete Google Play policy automation;
- HTML output;
- SARIF output;
- permission-risk classification;
- broad CLI redesign;
- unrelated refactoring.

These are not considered failures of M0.7. They are deliberate scope boundaries.

## 4. Engineering method

Every M0.7 block follows:

**ledger review → pre-change audit → scoped implementation → focused tests → second audit → Actions → follow-up → individual correction if required → new validation → checkpoint**

Additional rule:

**one capability boundary at a time.**

A block cannot absorb an adjacent capability merely because it becomes convenient during implementation.

## 5. Fixtures and regression strategy

Each cryptographic increment must include deterministic evidence for at least:

- valid supported case;
- malformed structure;
- cryptographically invalid case;
- unsupported algorithm/key combination;
- mixed multi-signer behavior where applicable;
- evidence retention after signer-local failure where applicable.

Existing M0.6 fixtures remain regression inputs and are not replaced by new fixtures.

Any fixture created for a block must be reachable from the active branch before the second audit.

## 6. CI strategy

M0.7 will use the established stacked-branch validation model.

For every block:

- source branch receives push validation;
- the active validated base workflow covers the stacked PR target;
- Build, Test, Format, and Clippy must pass;
- PR-event validation must be demonstrated where the branch structure requires it;
- CI trigger changes remain scoped to the active M0.7 stack.

No CI graph redesign is part of M0.7.

## 7. Error ledger discipline

Before every M0.7 audit/change cycle, review `docs/ERRORS-AND-FIXES.md`.

Every newly discovered failure or corrective event receives a new chronological `ERR-NNN` entry.

Historical entries are never rewritten or renumbered.

CI-only formatting/lint failures remain distinguishable from production defects.

## 8. Acceptance criteria

M0.7 is complete only when:

- every included block has a pre-change audit;
- every included block has a second audit;
- all declared supported cryptographic cases have real verification coverage;
- unsupported boundaries remain explicit;
- invalid cases cannot become Verified through fallback behavior;
- multi-signer evidence remains isolated and preserved;
- M0.6 regression coverage remains green;
- all required stacked CI validations pass;
- README and repository documentation match the actual capability boundary;
- final milestone audit and checkpoint are recorded;
- no unresolved production-code finding remains.

## 9. Baseline rule

The current M0.6 transition checkpoint remains the baseline until this definition is formally closed.

No M0.7 production branch or implementation commit is authorized by this document alone.

After Etapa 3 is formally closed, the first M0.7 implementation branch will be created from the validated M0.6 checkpoint lineage. The exact validated M0.6 checkpoint SHA will be recorded in the M0.7 checkpoint, and the branch base used for implementation will be stated explicitly before Block 1 begins.
