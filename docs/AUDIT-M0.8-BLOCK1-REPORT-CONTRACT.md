## 1. Scope under audit

M0.8 Block 1 will define the first versioned machine-readable report contract for Android Release Doctor.

The contract must expose current evidence without exposing internal Rust representation as the public API.

No production serialization code is included in this audit.

## 2. Mandatory engineering discipline carried forward

The current ledger was reviewed through ERR-076 before defining the block.

The ledger establishes that previous work is safest when it follows bounded edits, focused tests, second audit, Actions, and checkpoint closure. In particular, ERR-071 through ERR-076 demonstrate that broad source/CI changes can create structural or validation defects; this block therefore freezes the data contract before serialization implementation.

## 3. Current evidence model audited

The current `AuditReport` contains:

- artifact path, artifact kind, and size;
- artifact inventory;
- parsed manifest or manifest error;
- optional project information or project error;
- structured findings.

The inventory currently exposes:

- archive entries;
- manifest path;
- DEX files;
- native ABIs;
- native ELF evidence and parse errors;
- native ZIP evidence and parse errors;
- signature-file presence;
- APK signing-block structural evidence and error;
- APK cryptographic verification evidence and error.

The cryptographic model currently exposes:

- v2, v3 and v3.1 scheme results;
- explicit v3.1/v3.2 presence flags;
- Verified / Invalid / Unsupported scheme states;
- signer counts;
- algorithm IDs;
- signer certificate SHA-256 fingerprints;
- targeted SDK ranges;
- v3 rotation minimum SDK evidence;
- v3.1 development-release targeting evidence;
- proof-of-rotation state, lineage fingerprints and capability flags;
- scheme detail text.

The top-level finding model currently exposes:

- static rule ID;
- severity;
- title;
- summary;
- remediation.

The supported finding severities are PASS, WARNING, BLOCKER and MANUAL-REVIEW.

## 4. Findings from the pre-change audit

### Finding B1-01 — Do not serialize internal domain structs directly

**Result: PASS / constraint recorded.**

The public contract must not be generated by blindly serializing `AuditReport`, `Finding`, `ProjectInfo`, or cryptographic structs.

Reasons:

- internal Rust types include `PathBuf`;
- `Finding::rule_id` is an implementation-level `&'static str`;
- internal enum representation is not itself a compatibility promise;
- future internal refactors must not change the external report accidentally.

The implementation boundary should therefore introduce explicit report DTOs.

### Finding B1-02 — Preserve evidence state distinctions

**Result: PASS / mandatory invariant.**

The contract must preserve:

- evidence present and verified;
- evidence present and invalid;
- evidence present but unsupported;
- evidence not present;
- evidence not available because parsing/inspection failed;
- manual review requested by a rule.

These states must not collapse into a single boolean or a generic warning.

Examples:

- `v31_present: false` means the v3.1 block was inspected and was not present.
- `v31: null` means no v3.1 verification result exists.
- `apk_signature_verification: null` means no verification object was produced.
- `apk_signature_verification_error` records a separate inspection/verification error when one exists.

### Finding B1-03 — Collections preserve positive absence

**Result: PASS / invariant.**

A collection already produced by the engine remains an array even when empty.

For example:

- no native libraries → `native_libraries: []`;
- no permissions → `permissions: []`;
- no findings of a sub-type → corresponding array remains present if represented.

An empty array means the collection was inspected and contained no entries. It must not be substituted with `null`.

### Finding B1-04 — Optional objects preserve “not supplied/not available”

**Result: PASS / invariant.**

Fields derived from Rust `Option<T>` remain nullable.

Examples:

- `application: null` with non-null `manifest_error` means manifest parsing failed;
- `project: null` with non-null `project_error` means project analysis was requested but failed;
- `project: null` with null `project_error` means project evidence was not requested;
- `apk_signing: null` means no structural signing evidence object exists.

The contract must not synthesize placeholder values.

### Finding B1-05 — Manifest and project errors must remain explicit

**Result: CORRECTED BEFORE FREEZE.**

The first contract draft omitted the dedicated `manifest_error` and `project_error` fields even though both are real `AuditReport` evidence.

Correction:

- add required top-level nullable `manifest_error`;
- add required top-level nullable `project_error`;
- keep parsed `application` and `project` objects independent from their error fields.

No error text is moved into generic findings during serialization.

### Finding B1-06 — No timestamp in v1

**Result: PASS / deliberate exclusion.**

A generated timestamp is not currently part of the audit evidence and would reduce deterministic reproducibility.

M0.8 Block 1 therefore excludes timestamps from the stable report contract.

### Finding B1-07 — No artifact hash invented

**Result: PASS / deliberate exclusion.**

The engine currently records artifact path, type and size but does not calculate an artifact SHA-256.

The contract will not invent or require a hash until a bounded block explicitly adds one.

### Finding B1-08 — Play context needs an explicit envelope

**Result: OPENED FOR CONTRACT, not production behavior.**

Current `evaluate_play_policy` receives a platform and uses `PLAY_POLICY_VERSION`, but `AuditReport` itself does not retain that context.

The v1 contract therefore reserves an optional `play` object containing:

- requested platform;
- policy profile version.

Block 1 defines the shape. Population in production code is a scoped implementation concern and must not require changes to policy evaluation semantics.

### Finding B1-09 — Exit code is not report evidence

**Result: PASS / deliberate exclusion.**

The CLI currently maps blocker presence to a process exit code.

That behavior belongs to the CLI contract, not the evidence schema.

Block 1 therefore records counts but does not encode operating-system exit codes.

## 5. Frozen v1 report shape

Version 1 contains these top-level sections:

```text
schema_version
engine_version
artifact
application
manifest_error
inventory
project
project_error
play
findings
summary
```

The contract is versioned independently from the Rust engine version.

## 6. Compatibility rules

- Patch change: wording/metadata corrections without structural or semantic change.
- Minor change: additive optional fields that do not change existing meanings.
- Major change: field removal, type change, state-semantics change, or incompatible renaming.
- Consumers must key behavior from `schema_version`, not `engine_version`.

## 7. Serialization architecture constraint

Implementation must use explicit report DTOs and a dedicated serialization layer.

The current core evidence types remain internal domain evidence.

The serializer must be deterministic with respect to the same `AuditReport` input.

The text renderer remains available and is not replaced by JSON in this block.

## 8. Acceptance criteria for the contract definition

The definition is complete only when:

- every currently exposed evidence family has an explicit contract location;
- nullable vs empty semantics are documented;
- cryptographic state semantics are preserved;
- manifest/project errors are preserved explicitly;
- manual review is preserved at finding level;
- Play context has a defined extension point;
- timestamps, host-specific data and invented hashes are excluded;
- schema and compatibility versioning are explicit;
- no production behavior is authorized by the contract document alone.

## 9. Scope boundary

Included:

- report v1 semantics;
- field names/types;
- null/empty semantics;
- schema versioning;
- compatibility rules;
- serializer architecture constraints.

Excluded:

- serde implementation;
- CLI flags;
- exit-code redesign;
- GitHub Action;
- release packaging;
- new cryptographic capability.

## Result

**PRE-CHANGE AUDIT PASS. Contract omissions found during review were corrected before the second audit.**
