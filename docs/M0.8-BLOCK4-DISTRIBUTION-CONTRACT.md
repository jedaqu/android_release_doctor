# M0.8 Block 4 — Distribution / Release Packaging Contract

Date: 2026-10-01
Status: frozen implementation contract

## 1. Purpose

Produce reproducible end-user archives of the existing `android-release-doctor` CLI and provide a tag-driven GitHub Release publication path.

This block is packaging/orchestration only.

## 2. Supported first matrix

- `linux-x86_64` on `ubuntu-24.04`
- `windows-x86_64` on `windows-2025`
- `macos-x86_64` on `macos-15-intel`

## 3. Version contract

The workspace package version is the source of truth.

For a tag push:
- tag must begin with `v`;
- `TAG_VERSION = GITHUB_REF_NAME` without the leading `v`;
- `TAG_VERSION` must equal the workspace package version;
- mismatch fails before packaging;
- release publication requires `gh release create --verify-tag`.

No automatic tag creation or version mutation is permitted.

## 4. Build contract

Each platform job executes:

`cargo build --locked --release -p doctor-cli`

The produced binary must be the configured Cargo binary:
`android-release-doctor`

No custom release profile is introduced by this block.

## 5. Package contract

Linux:
`android-release-doctor-v<version>-linux-x86_64.tar.gz`

Windows:
`android-release-doctor-v<version>-windows-x86_64.zip`

macOS:
`android-release-doctor-v<version>-macos-x86_64.tar.gz`

Archive payload:
- binary;
- `LICENSE`;
- `README.md`.

## 6. Binary validation contract

Before upload, each native job verifies:
- executable is present;
- `--version` contains `android-release-doctor <version>`;
- `--help` succeeds;
- archive exists;
- archive contains only the expected payload files.

## 7. Checksum contract

The publish job computes:
`SHA256SUMS`

Each archive checksum is verified before the release is created.

The checksum file is included as a release asset.

## 8. Workflow trigger contract

The workflow runs for:
- pushes to `m08-block4-distribution-release`;
- pull requests targeting `m08-block3-github-action`;
- version tags matching `v*`.

Branch and PR executions validate packaging but never publish a release.

Tag executions publish only after all package jobs succeed.

## 9. Permissions contract

Default workflow permissions remain read-only.

The final release-publishing job explicitly requests:
`contents: write`

No other write permission is required.

## 10. Release publication contract

Publication is performed by:
`gh release create <tag> <assets...> --verify-tag`

Release notes use GitHub's generated release notes facility.

The release is not marked pre-release by this block.

## 11. Artifact transfer

Each platform package is first uploaded as an Actions workflow artifact using a unique artifact name.

The publish job downloads the three package artifacts, computes `SHA256SUMS`, verifies the checksums, and then publishes the four release assets.

## 12. Security constraints

- No third-party release publisher action.
- No user-supplied shell fragments.
- No secrets embedded in archives.
- No credentials copied into package contents.
- No implicit tag creation.
- No release publication from branch/PR events.
- No source-tree packaging.
