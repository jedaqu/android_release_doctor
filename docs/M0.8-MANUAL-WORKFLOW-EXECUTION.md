# M0.8 Manual Workflow Execution

M0.8 Block 3 and Block 4 support manual GitHub Actions execution through the GitHub Actions **Run workflow** interface.

## Manual execution is validation only

A manual execution is an operational validation path. It does not create a GitHub Release.

### Block 3

The manual run executes the Block 3 Action self-test:

- success path;
- blocker path;
- operational-error path;
- Report v1 JSON validation;
- exit-code contract validation.

### Block 4

The manual run executes the Block 4 distribution validation:

- workspace version validation;
- locked workspace tests;
- format and Clippy checks;
- Linux, Windows, and macOS x86_64 packaging;
- packaged binary `--version` and `--help` checks;
- archive-content verification;
- package artifact generation.

The Block 4 publication job remains guarded by both conditions:

- the event must be a tag push; and
- the ref must start with `refs/tags/v`.

Therefore a manual run can validate the complete distribution path without publishing a GitHub Release.

## Release publication boundary

A GitHub Release is published only through the existing version-tag path.

For a release such as `v0.1.0`:

1. the tag must point to the intended validated repository state;
2. the workspace version in `Cargo.toml` must match the tag version;
3. Block 4 must validate and package all supported platforms;
4. the publish job generates and verifies `SHA256SUMS`;
5. the workflow invokes GitHub Release creation with `--verify-tag`.

This separation is intentional:

**manual run = validation**

**version tag = publication**

## Future evolution

The manual execution surface is an incremental CI capability. Its workflow triggers and operational documentation may be improved as the release process evolves, while the publication guard must remain explicit and reviewable.
